🔄 Flujo completo de un Data Space

Etapas end-to-end (Operador → Onboarding → Conectores → Assets → Contratos → Transferencia → Evidencia → Revocación).

Operador: reglas, onboarding, servicios comunes Proveedor: publica assets/ofertas, entrega datos Consumidor: descubre, negocia, consume Servicios comunes: broker, trust, evidencia, etc.

iCómo leer estas etapas

1Dos “planos” siempre presentes
Control Plane (CP): registra assets, publica catálogos, negocia contratos, autoriza transferencias.
Data Plane (DP): mueve “bytes” (datos) y aplica controles técnicos durante la transferencia.
2Etapas con y sin datos reales
Antes de la transferencia, el Data Space opera casi solo con metadatos y políticas. Los datos reales viajan directamente entre proveedor y consumidor cuando existe contrato activo.
3Gratis vs De pago
Un asset “de pago” se define en la Oferta (Etapa 3), condiciona el Contrato (Etapa 5), impacta la Transferencia (Etapa 6) y se registra en Auditoría (Etapa 7) para facturación.
Idea clave: el “marketplace/portal” es la interfaz humana; los conectores son el mecanismo técnico para soberanía, negociación y transferencia segura.
Qué obtienes con este documento: una guía por etapas (0 a 8), un diagrama completo, y un glosario para tu documentación.

0Etapa 0 — Preparación del Data Space por el Operador

🧭 Operador / Gobernanza
Reglas, niveles de confianza, onboarding, políticas del ecosistema
→
🧩 Servicios comunes
Broker (catálogo), Trust Registry, Evidencias, Portales/APIs
→
🪪 Identidad y confianza
mTLS / OIDC, CA/Trust anchors, atributos/claims, revocación
1Definir gobernanza
Quién puede entrar, niveles de confianza, reglas de publicación/uso, auditoría, disputas y sanciones.
2Definir identidad y confianza
Certificados aceptados (CA/anchors), mTLS, OIDC/JWT, rotación/expiración, listas de confianza.
3Desplegar servicios comunes
Broker (si aplica), registro de participantes (trust registry), evidencias/auditoría (clearing house o equivalente), portales y APIs de operador.
☁️ AWS típico
Route53 + ACM + WAF (exposición segura)
EKS/ECS/Lambda (servicios del operador)
RDS/DynamoDB (persistencia)
S3 (documentos/contratos/evidencias)
CloudWatch + KMS/Secrets Manager
🧠 Programación
Infra as Code (Terraform/CDK)
APIs de onboarding/registro/administración
Controles de seguridad y observabilidad
📌 Nota (IDS/Gaia-X/Catena-X)
Los ecosistemas comparten conceptos (identidad, confianza, catálogos, contratos, evidencias), pero pueden usar implementaciones distintas (p.ej., Tractus-X/EDC + OIDC/mTLS + registro de confianza).
Resultado de la etapa 0: el Data Space queda “operable” (reglas + servicios comunes + identidad/confianza), listo para onboardear participantes.

1Etapa 1 — Onboarding de Participantes

🏢 Participante
Puede ser proveedor, consumidor o ambos
→
🧾 Portal del Operador
Registro, verificación, aceptación de términos
→
🔐 Trust / IdP
Certificados, claims/roles, trust store, revocación
↓
📜 Trust Registry
Alta de organización y atributos confiables (si aplica)
→
🔌 Registro del conector
Endpoints CP/DP, health checks, datos técnicos
1Registro de organización y usuarios
Alta del participante (provider/consumer/ambos) y de usuarios humanos (portal).
2Verificación y aceptación
Verificación legal (según reglas) + aceptación del marco de gobernanza.
3Emisión/registro de certificados y atributos
Certificados (mTLS) + atributos (roles/claims) en IdP/Trust (según el modelo del espacio).
4Registro del conector (CP/DP)
Guardar endpoints, validar reachability, health, y prerequisitos de seguridad.
☁️ AWS típico
Cognito (login humano) o IdP federado
RDS (participantes/estados)
Secrets Manager/KMS (claves)
CloudWatch (logs onboarding)
📌 Cuándo NO participa
Normalmente Broker y Clearing House no son obligatorios aquí (salvo eventos administrativos).
Resultado de la etapa 1: el participante queda habilitado (identidad/roles + registro técnico del conector) para operar en el Data Space.

2Etapa 2 — Activación del Conector del Participante

🔌 Conector (Participante)
Despliegue CP/DP + configuración de seguridad
→
🔐 mTLS / OIDC
Trust store, validación de identidad, expiración/rotación
→
✅ Health & Reachability
Pruebas de conectividad y endpoints (CP/DP)
1Desplegar CP/DP
Control Plane (catálogo/negociación/autorización) + Data Plane (transferencia).
2Configurar mTLS y truststore
Certificados, trust anchors, validación de cadena, y (si aplica) OCSP/CRL.
3Configurar identidad (OIDC/JWT)
Issuer confiable, audiencias, claims/roles; políticas de expiración/renovación de tokens.
4Comprobar “health”
Verificar endpoints del CP/DP, DNS/TLS, rutas, y seguridad de red.
☁️ AWS (si el conector vive en tu infra)
EKS/ECS (deploy) + ALB/NLB (exposición)
VPC/Security Groups (red)
ACM (TLS) si aplica
CloudWatch (observabilidad)
📌 Cuándo NO participan
Broker y Clearing House todavía no son obligatorios.
Resultado de la etapa 2: conector listo y seguro (CP/DP) para publicar assets y operar negociaciones/transferencias.

3Etapa 3 — Creación y Publicación de Data Assets

👤 Proveedor
Crea Asset + Policy + Offer y publica
→
🧠 Control Plane (Proveedor)
Registra metadatos y expone catálogo (no datos)
→
📚 Broker (opcional)
Indexa metadata para discovery centralizado
1Creación del Data Asset
Metadatos (nombre, descripción, dominio, tipo, formato, versión) + referencia técnica (S3 path / API / DB).
El asset no contiene el dato: contiene la referencia y configuración para que el DP acceda cuando toque.
2Definición de Policy (ejecutable)
Quién accede (rol), propósito, vigencia, límites, geografía, obligaciones (atribución, no redistribución, etc.).
3Creación de Offer (Oferta)
Offer = Asset + Policy + condiciones.
Incluye precio y estado (publicado/despublicado):
Gratis De pago
4Publicación
El Control Plane expone el catálogo (por protocolo si aplica). Otros conectores/portales pueden descubrirlo.
📌 Importante: El Broker indexa metadatos; no toca datos reales. El Data Plane aún no participa.
☁️ AWS típico
Backend portal (si creas assets desde UI)
RDS/DynamoDB (catálogo interno/espejo)
S3 (si el recurso es archivo / plantillas / esquemas)
CloudWatch (logs)
🧩 Programación
APIs Asset lifecycle (create/update/publish)
Validación de campos y estados (DRAFT/PUBLISHED/DEPRECATED/ARCHIVED)
Versionado técnico y (si aplica) semántico
📌 Catena-X / federación
Puede haber discovery directo entre conectores (sin broker obligatorio) dependiendo del patrón del ecosistema.
Resultado de la etapa 3: el asset queda visible en catálogo (directo o vía broker) con policy y offer (incluyendo si es gratis o de pago).

4Etapa 4 — Descubrimiento de Assets

🔍 Consumidor
Busca assets y revisa policies/ofertas
→
📚 Broker (si existe)
Búsqueda centralizada (metadatos)
→
🧠 Catálogo del Proveedor (CP)
Detalle real de ofertas/policies (catálogo “source of truth”)
1Búsqueda
El consumidor busca vía Broker o consulta directa a catálogos de proveedores (peer-to-peer).
2Revisión de la oferta
Visualiza policy, restricciones, y si el asset es Gratis o De pago.
3Decisión
Si cumple requisitos, inicia negociación (Etapa 5). Si no, continúa buscando.
GET /catalog?query="movilidad"&price=paid|free Response: { "results": [ { "assetId": "asset-001", "title": "Tráfico en tiempo real", "priceType": "paid" }, { "assetId": "asset-002", "title": "Calendario de eventos", "priceType": "free" } ] }
📌 Cuándo NO participa
Clearing House no participa; Data Plane no participa.
☁️ AWS típico
Frontend (búsqueda humana)
Backend (agregación/filtrado)
Cache opcional (ElastiCache/Redis)
Resultado de la etapa 4: el consumidor identifica una oferta compatible (y entiende si es gratis o de pago) antes de iniciar negociación.

5Etapa 5 — Negociación y Contrato

🧠 CP Consumidor
Inicia negociación por una Offer
⇄
🧠 CP Proveedor
Evalúa policy, identidad, atributos y decide
🔐 IdP / Trust
Valida identidad (mTLS/OIDC) y claims/roles
→
🧾 Evidencia (opcional)
Clearing House / ledger: “contract signed”
1Inicio de negociación
El consumidor selecciona una Offer e inicia una Contract Negotiation desde su CP hacia el CP del proveedor. No hay transferencia; todo ocurre en CP.
2Creación del Contract Agreement
Si es exitoso, se crea el Agreement en ambos CP (IDs, vigencia, policy, participantes). El contrato operativo vive en los conectores.
3Si el asset es de pago
El acuerdo pasa por estado “pendiente” hasta pago y firma (según tu gobernanza).
De pago → contrato condicionado a pago.
4Estados típicos
Solicitado → Rechazado / Pendiente de firma-pago → Firmado-pagado → Aceptado/ACTIVE → TERMINATED (expirado/revocado).
☁️ AWS típico (si haces contrato “interno”)
RDS (estado del agreement)
KMS (firmas internas)
S3 Object Lock (contratos/evidencias inmutables)
CloudWatch (audit logs)
QLDB opcional (ledger)
📌 Cuándo NO participa
Data Plane no participa aún.
Resultado de la etapa 5: existe un contrato/Agreement operativo (ACTIVE o condicionado a firma/pago) que habilita la transferencia en la siguiente etapa.

6Etapa 6 — Transferencia / Consumo del Dato

🧠 CP Proveedor
Autoriza: identidad + contrato ACTIVE + policy cumplida
→
🚚 Data Plane
Mueve bytes (pull/push/proxy) y aplica controles técnicos
→
📥 Consumidor
Recibe datos bajo restricciones del contrato
🧾 Evidencia (opcional)
Eventos: transfer_started / transfer_completed
→
🔐 Revalidación
Token/cert válido, no revocado, vigencia OK
1Validación previa (CP)
Identidad válida (mTLS/OIDC), Agreement ACTIVE, vigencia, policy (propósito, límites, geografía), no revocado. Si falla → no se inicia transferencia.
2Orquestación del transfer process
El consumidor inicia un Transfer Process; el CP crea transferProcessId y ordena al DP ejecutar.
3Ejecución (DP)
DP accede al recurso real (S3/API/DB) y transfiere (pull/push/proxy) usando TLS/mTLS. No guarda el dataset permanentemente.
4Si el asset es de pago
El CP puede bloquear/limitar la transferencia hasta confirmar “pago OK”. De pago → habilitación condicionada.
☁️ AWS típico
S3 (dataset) + KMS (cifrado)
Signed URLs (entrega controlada) / IAM roles DP
API Gateway/Lambda/ECS (si es API-based)
CloudWatch (logs/métricas)
🧩 Programación
Orquestación transfer process + validación policy/contract
Emisión de credenciales temporales (JWT / signed URL)
Manejo de errores, retries y métricas de uso
Resultado de la etapa 6: datos transferidos/consumidos solo si contrato/policy lo permiten (y si es de pago, con la condición cumplida).

7Etapa 7 — Auditoría y Evidencia

🧾 Clearing House / Ledger
Evidencias: contrato, transfer, rechazos, consumo
←
📜 Logs Conectores
Eventos normalizados + hashes/firmas
→
📌 Auditoría / Compliance
Trazabilidad y no repudio
1Registrar eventos
contract_created/signed, transfer_started/completed, descargas, rechazos, revocaciones.
2No repudio
Hash chaining, timestamps, firmas (si aplica). El clearing guarda evidencia, no datos.
3Si es de pago
Registrar consumos (requests/GB/descargas) para facturación y disputas.
☁️ AWS típico
CloudWatch Logs (eventos)
S3 Object Lock (evidencias)
QLDB opcional (ledger)
🧩 Programación
Event model normalizado
Firma y hash chaining si aplica
APIs/consultas de auditoría
Resultado de la etapa 7: trazabilidad verificable (quién/qué/cuándo/contrato) sin exponer datos, habilitando compliance y facturación si aplica.

8Etapa 8 — Revocación, Expiración, Rotación

🔐 Certs / Tokens
Expiran o se revocan → bloqueo mTLS / renovación OIDC
→
🧠 Conector (enforcement)
Revalida por transferencia/negociación
→
🔔 Operación
Alarmas, jobs programados, notificaciones
1Certificados vencen/revocan
Se bloquea comunicación mTLS (fallará en handshake o validación de cadena/revocación).
2Tokens expiran
Se renuevan con IdP (OIDC). Si no, el CP/DP rechaza requests.
3Contratos expiran o se revocan
Acceso se revoca (CP no autoriza transferencias nuevas; DP no debe continuar).
4Políticas cambian
Se generan nuevas ofertas/versiones; las anteriores pueden deprecarse/archivarse.
☁️ AWS típico
CloudWatch alarms (expiración)
Secrets Manager/ACM (rotación)
EventBridge (jobs programados)
Notificaciones (SNS/Email)
🧩 Programación
Lifecycle management (certs/tokens/contracts)
Revalidación en cada negociación/transfer
Notificaciones y remediación
Resultado de la etapa 8: el ecosistema se mantiene seguro y vigente en el tiempo (rotación/revocación) sin romper la soberanía ni la gobernanza.
